# HUG-255 — Firebase Hosting with `/api/**` rewrite (per-issue plan)

## Goal

Serve the Vite SPA at `<project>.web.app` via Firebase Hosting. Use Firebase's `rewrites.run` to proxy `/api/**` to Cloud Run `hughes-api` (so the SPA stays same-origin and the existing relative `/api` client.ts works unchanged).

## Key decisions for this issue

### 1. Solve the path-prefix mismatch via FastAPI `root_path`, not router prefix

Three options were considered for the `/api` vs `/threads` mismatch (Vite dev proxy strips `/api`; Firebase Hosting does not). Chosen path:

- **`FastAPI(root_path=os.environ.get("API_ROOT_PATH", ""))`** in `packages/api/src/api/main.py` (already landed in HUG-254).
- Cloud Run sets `API_ROOT_PATH=/api` (also landed in HUG-254's deploy script).
- Local dev leaves it unset → `root_path=""`, routes resolve at `/threads`.

This is reversible (just remove the env var), keeps test paths unchanged (still `/threads`), and doesn't change anything in `vite.config.ts`.

### 2. Use the `tryhughes` GCP project's Firebase site

`tryhughes` already has Firebase Hosting enabled (the API was enabled by `infra/setup.sh`). The default Firebase Hosting site name is `tryhughes` (same as the project ID). It will be available at:
- `https://tryhughes.web.app`
- `https://tryhughes.firebaseapp.com`

If the default site is already used by something else, `firebase init hosting` will let me pick a different site name (e.g., `hughes-app`).

The existing `hughes-website` Cloud Run service at `www.tryhughes.com` is independent of Firebase Hosting (Cloud Run domain mapping ≠ Firebase Hosting); no conflict.

### 3. Aggressive caching on hashed assets, no-cache on `index.html`

Vite already hashes asset filenames (`assets/Foo-A1B2C3D4.js`), so a long max-age is safe. `index.html` references the hashed names, so it must be no-cache for SPA shell updates to propagate.

### 4. Firebase auth via gcloud Application Default Credentials, with manual-deploy fallback

`firebase login` is interactive. To stay autonomous, `deploy-frontend.sh` tries:
1. `firebase deploy --project tryhughes --only hosting` directly (firebase-tools 13+ accepts gcloud user credentials via `GOOGLE_APPLICATION_CREDENTIALS` / ADC).
2. If (1) fails with an auth error, the script prints clear "run `firebase login` once and re-run me" instructions and exits non-zero.

`deploy-frontend.sh` does NOT auto-run `firebase login` (interactive flow can't be scripted cleanly).

### 5. The `serviceId` in `firebase.json` references the Cloud Run service in `europe-west1`

The `run:` rewrite needs `serviceId: hughes-api` and `region: europe-west1`. This binds Firebase Hosting's request proxying to the specific Cloud Run service deployed by HUG-254.

## Test plan

After `bash infra/deploy-frontend.sh`:

1. `curl -sI https://tryhughes.web.app/` → 200, `Cache-Control: no-cache` on index.html.
2. `curl -sI https://tryhughes.web.app/api/health` → 200 (proves rewrite reaches Cloud Run and `API_ROOT_PATH=/api` works).
3. Browser test: open `https://tryhughes.web.app/`, SPA renders, submit an NL question, SSE answer streams back.
4. `gcloud run services logs read hughes-api --region europe-west1` shows the Firebase-originated requests.
5. Direct Cloud Run URL still 403 unauthenticated (defense-in-depth verified).
