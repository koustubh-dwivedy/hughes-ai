# HUG-253 — Bootstrap demo data into Cloud SQL (per-issue plan)

## Goal

Apply the existing 17 migrations, run `make seed --profile small_cu`, and run `make dbt-build` — all against the live Cloud SQL `hughes-pg` instance created by HUG-252.

## Key decisions for this issue

### 1. Use Cloud SQL Auth Proxy v2 (download on demand)

`psql` and `cloud-sql-proxy` are not installed on the operator's machine. Asking the user to `brew install` is a manual prereq we can avoid: `bootstrap.sh` auto-downloads the Cloud SQL Auth Proxy v2 static binary to `~/.cache/hughes-ai/cloud-sql-proxy` on first run.

Why Auth Proxy v2 specifically:
- Pure Go static binary — no system deps.
- TCP tunnel on `localhost:5433` works seamlessly with `psycopg`, `dbt-postgres`, and any other Postgres client without auth-token plumbing.
- v2's `--port` flag avoids the v1 instance-string mess.

### 2. Apply migrations via a small Python wrapper, not `psql`

`psql` isn't installed locally. Rather than make it a prereq, `bootstrap.sh` calls a 30-line Python wrapper (`scripts/apply_migrations.py`) that:
- Opens a `psycopg.connect()` to `localhost:5433` as `cubi_migrate`.
- Iterates `migrations/*.sql` in numeric order.
- Runs each file's SQL in a single transaction.

This is roughly equivalent to what the Makefile's `migrate` target does for the local Docker container, just adapted to TCP.

### 3. Grant `INSERT ON audit_log TO cubi_runtime` AFTER migrations

The `audit_log` table is created by one of the migrations (need to find which — likely `001_lending_schema.sql` or `010_readonly_grants.sql`). The `cubi_runtime` role needs explicit `INSERT` on it, and a grant can only be issued after the table exists. `bootstrap.sh` adds this grant as the last SQL step, after migrations have completed.

### 4. Set DBT env vars for the Cloud SQL connection

`packages/dbt-models/profiles.yml` reads `DBT_HOST`, `DBT_PORT`, `DBT_USER`, `DBT_PASSWORD`, `DBT_DBNAME`. `bootstrap.sh` exports these pointing at the Auth Proxy's `localhost:5433` for the duration of `make dbt-build`.

### 5. Source the migration password from Secret Manager

`bootstrap.sh` reads the `database-url-migrate` Secret Manager secret to get the `cubi_migrate` password (set/rotated by `setup.sh`). The script parses the URL to extract user, password, db name. Never echoes the password.

### 6. Idempotency

`make seed` is deterministic (seed=42) and uses a content-hash cache — re-running on the same DB re-asserts the same rows. `make dbt-build` is also idempotent (models materialize or re-materialize). Migrations are idempotent by repo invariant (each file uses `IF NOT EXISTS` / `IF EXISTS`). Net: `bootstrap.sh` is safe to re-run.

## Files to create

- `infra/bootstrap.sh` — orchestrator.
- `scripts/apply_migrations.py` — small Python wrapper that runs the 17 SQL files via psycopg.
- `scripts/verify_seed.py` — asserts row counts match the `small_cu` profile.

## Test plan for this issue

After running `bash infra/bootstrap.sh`:

1. `python3 scripts/verify_seed.py` (called automatically at end of bootstrap) returns 0; asserts:
   - `SELECT COUNT(*) FROM members;` ≥ 3000
   - `SELECT COUNT(*) FROM deposit_accounts;` ≥ 8000
   - `SELECT COUNT(*) FROM loan_applications;` ≥ 500
2. `packages/dbt-models/target/manifest.json` exists.
3. Idempotency: re-run `bash infra/bootstrap.sh` — exit 0, row counts unchanged.
4. Read-only role check (executed at end of bootstrap):
   - As `cubi_runtime`, `SELECT count(*) FROM members` returns a number.
   - As `cubi_runtime`, `INSERT INTO members (...) VALUES (...)` fails with permission denied.
   - As `cubi_runtime`, `INSERT INTO audit_log (...)` succeeds.
