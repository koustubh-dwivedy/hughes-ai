# HUG-252 — Provision GCP data plane (per-issue plan)

## Goal

Stand up the GCP resources the app needs at runtime:
- Cloud SQL Postgres `hughes-pg` (`db-f1-micro`, POSTGRES_16, `europe-west1`).
- Database `cubi` with `pgvector` installed.
- DB roles: `cubi_migrate` (owner; future migrations) and `cubi_runtime` (read-only; what Cloud Run connects as).
- Artifact Registry `hughes` (Docker, `europe-west1`).
- Three Secret Manager secrets: `database-url` (runtime), `database-url-migrate` (bootstrap-only), `ollama-api-key`.
- Dedicated runtime service account `hughes-api-sa@tryhughes.iam.gserviceaccount.com` with `secretmanager.secretAccessor` on the two relevant secrets and `cloudsql.client` at project level.

## Key decisions for this issue

### 1. Drop the third role `cubi_audit`

Original plan had three roles: `cubi_migrate`, `cubi_runtime`, `cubi_audit`. Reviewing the HUG-257 test plan, the runtime role needs to:
- SELECT on application tables
- INSERT on `audit_log` only (no UPDATE/DELETE)

This is achievable with a single role (`cubi_runtime`) + targeted grants. Adding a third role just to hold the audit INSERT permission is over-engineering. Simpler model: `cubi_runtime` gets `SELECT` on all tables via default privileges, plus an explicit `INSERT` on `audit_log` (added by `bootstrap.sh` in HUG-253, after the migration that creates the table has run).

### 2. Use `gcloud sql connect` for one-shot SQL, not the Cloud SQL Auth Proxy

`setup.sh` needs to run `CREATE EXTENSION vector;` and a handful of grants. `gcloud sql connect` auto-allowlists the caller's public IP for the session and uses an embedded SQL Proxy when the API supports it. No additional binary required, no Auth Proxy lifecycle to manage in the script.

The Auth Proxy IS still used in `bootstrap.sh` (HUG-253) for the longer-running migration / seed / dbt-build steps.

### 3. Storage policy + backups

- 10 GB SSD, auto-increase enabled — `small_cu` profile is well under 1 GB seeded; the headroom is for dbt materializations and growth.
- Daily backups at 03:00 UTC, 7-day retention. Default Cloud SQL behavior; documented for runbook completeness.

### 4. Runtime DB role gets a randomly-generated password

Generated by `openssl rand -base64 32 | tr -d '\n='` (truncates newlines and equals signs that could confuse psql / URL parsing). Stored in Secret Manager as part of the full `DATABASE_URL` connection string. Never echoed to stdout. If the user (or anyone) needs to re-fetch it, the source of truth is `gcloud secrets versions access latest --secret=database-url`.

### 5. Idempotency

Every `gcloud ... create` is preceded by a `describe` check. APIs are enabled via `gcloud services enable` (naturally idempotent). Secrets use `versions add` when the secret already exists.

The one non-idempotent step is the role-password rotation: every run of `setup.sh` generates a new password and updates the `database-url` secret. **This is intentional** — re-running the script in production rotates credentials. The previous secret version is preserved (Secret Manager keeps history), and Cloud Run picks up the new version on next deploy.

### 6. Region choice: `europe-west1` (not `us-central1`)

Per the AUTONOMOUS_RUN_LOG decision: the existing `tryhughes` project services (`hughes-website` Cloud Run, `gcf-artifacts` Artifact Registry) all live in `europe-west1`. Cross-region Cloud Run ↔ Cloud SQL would add latency and cost. Staying in-region simplifies the Unix-socket integration (`host=/cloudsql/<conn-name>`).

## Files to create

- `infra/setup.sh` — main provisioning script (idempotent).
- `infra/sql/init.sql` — `CREATE EXTENSION vector;` + role grants (run via `gcloud sql connect`).
- `infra/README.md` — initial skeleton with the "GCP project provisioning" section.

## Test plan for this issue

After running `bash infra/setup.sh`:

1. `gcloud services list --enabled --project=tryhughes | grep -E 'run|sqladmin|secretmanager|artifactregistry|firebasehosting|cloudbuild'` — all 6 present.
2. `gcloud sql instances describe hughes-pg --project=tryhughes` — POSTGRES_16, db-f1-micro, europe-west1.
3. Connect via `gcloud sql connect`: `psql -c "\dx"` → `vector` extension listed; `psql -c "\du"` → roles `cubi_migrate` and `cubi_runtime` present.
4. `gcloud secrets list --project=tryhughes | grep -E 'database-url|ollama-api-key'` — three secrets.
5. `gcloud artifacts repositories describe hughes --location=europe-west1 --project=tryhughes` — exists.
6. `gcloud iam service-accounts describe hughes-api-sa@tryhughes.iam.gserviceaccount.com --project=tryhughes` — exists.
7. Idempotency: re-run `bash infra/setup.sh` — exit 0, no errors, secret version count goes up by 1 (intentional password rotation).
